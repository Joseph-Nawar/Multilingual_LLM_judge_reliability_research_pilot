# Research repository instructions

- Treat `docs/research/` as the authority for the study protocol, dataset, analysis, and integrity requirements. Keep implementation guidance here concise.
- This is an exploratory study of LLM judges. Canonical task states and executable validity rules define reference labels; model judgments never do.
- P1/P2 authoring and the P3 local infrastructure and development feasibility work are accepted. The four-scenario P2B feasibility pilot is concluded with documented limitations; do not reopen it or alter its review record. The main-study dataset still requires the two already commissioned independent bilingual reviewer submissions, documented resolution of substantive issues, deterministic revalidation, and a pre-inference freeze before any locked inference. The owner has authorized a narrow H2 diagnostic on eligible development data only; keep it separate from ordinary judging and never expose reference verdicts to inference. Keep all prototypes, scenarios, translations, coverage maps, annotations, prior versions, reviewer records, and reference data under ignored `.research-data/`; never stage or publish them.
- Do not alter existing human annotations or infer human validation from automated checks. The approved research execution path uses the local Gemma judge and local translation setup with $0 paid API expenditure. No remote inference, paid calls, locked evaluation before validation/freeze, or P4/P5 work is authorized. Structural/oracle checks do not establish bilingual semantic validation; pilot dependence disagreements remain unresolved and must not be presented as adjudicated or independently validated labels.
- Record methodological choices as proposals until reviewed by the research owner. Codex implements and documents decisions; it is not the final authority on scientific correctness.
- Prefer Python's standard library. Keep dependencies small, preserve raw evaluation records in future runners, and document deviations and exclusions.
- Use Python 3.11 or newer and pytest for deterministic checks. Run `python -m pytest` after changes that affect the project foundation.
- Keep canonical reference data and future judge-facing material on separate access paths. Machine checks of span coverage do not establish linguistic equivalence; do not mark Codex-authored language drafts as human validated.
- Before committing, inspect staged paths and verify no `.research-data/`, private, locked, reference, or unapproved study data are tracked.
- Develop on focused branches and make meaningful commits attributed to the owner's verified GitHub identity. After tests and safety checks, merge each completed milestone into the default branch through a pull request, preserving history with a normal merge. Never create empty or artificial commits for contribution counts, rewrite history to manipulate contribution dates, leave completed work indefinitely on feature branches, or publish private research data.
